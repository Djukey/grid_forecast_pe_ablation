# Does positional encoding matter for a small 24-hour load forecaster?

A controlled, seeded ablation of a 26,000-parameter transformer that forecasts the next 24 hours of electricity demand, run end to end on **one Tesla T4 (free Colab tier) in about 2 minutes**. The question: which positional encoding (`none`, `sinusoidal`, `learned`) should a small utility analytics team carry into a real-data pilot, and how much should it trust that choice? The budget: one GPU, 3 seeds per setting, 10 epochs, synthetic data, the whole study repeated 3 times.

## Result, with its bounds

On this synthetic series, with this model size, 10 epochs and 3 seeds per setting:

- **Sinusoidal encoding lowers test error by 0.41 MW (40%) compared with no positional encoding.** The 95% confidence intervals do not overlap (1.006–1.014 MW against 0.536–0.669 MW).
- **`learned` cannot be ranked.** Its seeds range from 0.72 to 1.00 MW, so its interval (0.43–1.20 MW) overlaps both other settings.
- **No setting is shown to beat a copy of the same hour last week (0.564 MW).** Sinusoidal's interval contains that value. The honest reading is "sinusoidal is the only model clearly better than no position information", not "the model is better than the baseline".
- **Cost does not separate the settings.** All three train in about 4.4 s and answer one forecast in about 0.75–0.77 ms (median) on this T4, using about 110 MB of GPU memory.

## Reproduce

Needs Python 3.10+ and the pinned libraries. A GPU is optional: the study reproduces the same accuracy numbers on CPU (to three decimals) but takes about 22 minutes on a 2-core CPU instead of 2 on a T4.

```bash
git clone <repository-url> && cd grid-forecast-pe-ablation
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python run.py --config config_smoke.yaml --out results_smoke   # pipeline check, about 30 s on CPU, NOT the reported study
python run.py                                                  # full study; rewrites results/
python run.py --figures-only                                   # redraw both figures from the committed CSV files, no GPU needed
```

On Colab: upload the zip and `run_in_colab.ipynb`, choose a T4 runtime, run all. The notebook only calls `run.py` and prints any mismatch between installed and pinned library versions.

Everything the run writes to `results/`: `runs.csv` (27 raw rows), `summary.csv` and `summary.md`, `checks.json` (baseline, determinism, data checksum), `example_forecast.csv`, `environment.json` and `hardware_footnote.txt` (logged automatically), `requirements_used.txt`, and the two figures, which are drawn only from those files.

## Intended use and out-of-scope use

**Intended use.** Evidence for one engineering decision: which positional encoding to carry into a real-data pilot of a small day-ahead demand forecaster, and how large the seed noise is when comparing settings on one GPU. It is also a template for reporting a small ablation with hardware, seeds, uncertainty and a baseline.

**Out of scope.** Operational load forecasting, dispatch, power purchasing or any decision about a real grid. Any claim about real demand, holidays, outages, extreme weather or other regions. Use as validation evidence for a regulator or customer. Safety-relevant uses. The MW values describe a synthetic series and must not be quoted as expected accuracy anywhere else.

## Data provenance and licensing

- **Fully synthetic.** `make_demand()` in `run.py` generates 730 days (17,520 hours) of hourly demand for one hypothetical rural distribution area: morning and evening peaks, lower weekends, winter heating and summer cooling driven by a synthetic temperature, and Gaussian noise. Seed `data_seed: 42`.
- **No real, personal or third-party data.** No external dataset, so no third-party licence applies. The generator and the generated data are released under the MIT licence (`LICENSE`).
- **Integrity check:** the SHA-256 of the generated `data/demand.csv` is stored in `results/checks.json`.
- **Split:** by time. The first 80% (14,016 hours) trains the model and the last 20% (3,504 hours, roughly August to December of the synthetic calendar) tests it. Normalisation uses training statistics only. That gives 3,457 training windows (every 4th window) and 3,481 test windows.

## Model and software versions

- **Model:** a transformer encoder (2 layers, width 32, 4 heads, no dropout) trained from scratch; no pretrained weights. It reads 168 hours and predicts the next 24. Only the positional encoding differs between settings (`none`; fixed `sinusoidal`, after Vaswani et al., 2017; `learned` table of 168 × 32 values). Training: Adam, learning rate 0.001, mean-squared-error loss, 10 epochs, batch size 128, no early stopping.
- **Libraries (pinned in `requirements.txt`):** torch 2.11.0, numpy 2.1.3, pandas 2.2.3, matplotlib 3.10.0, pyyaml 6.0.3. Reference run: Python 3.13.16.
- **Dataset version:** code version + `data_seed: 42` + the checksum above.

## Evaluation protocol

1. 3 settings × 3 seeds (0, 1, 2); each run trains from a freshly seeded model.
2. **Accuracy:** MAE in MW over all 24 horizon steps of all 3,481 test windows, after undoing the normalisation. Reported as mean and SD over seeds, with a 95% CI from the t-distribution (2 degrees of freedom, t = 4.303).
3. **Noise rule:** two settings differ only if their 95% CIs do not overlap. The same rule compares each setting with the baseline value. A first analysis used "min–max seed ranges do not overlap", which called all three differences real; that rule was too generous and was replaced.
4. **Baseline:** "same hour last week" (seasonal naive; Hyndman & Athanasopoulos, 2021) copies the demand from exactly 168 hours earlier, with no training.
5. **Latency:** one forecast at a time (batch 1), 20 untimed warm-up calls, then 200 timed calls, with the GPU synchronised before and after each call. p50 and p95 are computed per run.
6. **Peak memory:** `torch.cuda.max_memory_allocated()` per run (tensors only; the CUDA context is not included).
7. **Repeats:** the whole study is re-executed 3 times with the same seeds. This tests determinism and timing spread. It does not add seeds, so accuracy statistics never pool the repeats.

## What is held fixed

Same data and `data_seed`; same time-based split and test windows; same seeds in every setting; same architecture, optimiser, learning rate, batch size, epochs and training stride; same evaluation and latency code. One difference belongs to the factor itself: `learned` has 5,376 more trainable parameters (31,640 against 26,264) because the position table *is* the learned encoding.

## Compute budget: what the claims are bounded by

| | |
|---|---|
| **Budget** | One Tesla T4 (14.56 GB), one session, 2.2 minutes of wall-clock for 27 training runs. |
| **Memory was not the constraint** | Peak 110 MB against 14.56 GB (about 135× headroom), so no gradient accumulation or batch reduction was needed. |
| **Raw compute was not the constraint either** | One training run is about 0.89 TFLOP (PyTorch FLOP counter, matrix multiplies only) and takes about 4.4 s, roughly 0.2 TFLOP/s. A T4's FP32 peak is in the single-digit TFLOP/s (NVIDIA, n.d.), so this tiny model leaves the GPU mostly idle. A faster or second GPU would not speed it up. |
| **What actually bounds the claims** | The protocol chosen to match the first version of this study: 3 seeds, synthetic data, one model size, one learning rate, one test period. |
| **Not swept** | More than 3 seeds; per-setting learning rate or epochs; model width, depth and look-back; forecast horizon; real data; other seasons. |
| **What a larger budget would change** | 10 seeds instead of 3 (90 runs with the 3 repeats) would take about 7 minutes in total on this T4 and would narrow the confidence intervals about 3.5× (t drops from 4.30 to 2.26 and the divisor grows from √3 to √10, assuming the same SD). That is the experiment needed to settle sinusoidal against the baseline and to rank `learned`. Real data and several seasons would change more than any extra GPU. |

## Known failure modes

- **`none` forecasts a flat line.** Attention followed by averaging over hours ignores the order of the hours, so the model cannot tell morning from evening. The example forecast shows this: it predicts about 8.4 MW for every hour while the true curve swings between 7 and 12 MW.
- **`learned` is unstable across seeds.** One seed reached 1.00 MW, close to the no-encoding error, while two reached about 0.72 MW. I did not record training curves, so I cannot say whether that seed had not converged in 10 epochs or settled in a poor solution.
- **`sinusoidal` underestimates peaks.** In the example day it predicts about 10 MW at the morning peak where the actual value is about 11.7 MW.
- **No setting handles regimes it did not train on** (holidays, outages, heat waves). None of that was tested.

## Limitations

1. **Synthetic data.** Real demand has holidays, forecast-weather errors, outages and customer behaviour this generator lacks. Treat the MW values as illustrative; the direction of the real-world ranking is unknown, and a real series could favour either the baseline or the models.
2. **Three seeds per setting.** The intervals are wide (±0.39 MW for `learned`). Only the none-versus-sinusoidal gap (0.408 MW against half-widths of 0.004 and 0.067 MW) is large enough to rely on. Discount every other ordering to "undetermined".
3. **No tuning and no convergence check.** All settings share one learning rate and 10 epochs, chosen in advance, with no validation split and no recorded loss curves. If `learned` needs more epochs, this protocol understates it. The sinusoidal advantage may shrink under per-setting tuning.
4. **One test period.** The test windows cover roughly August to December of one synthetic year and overlap heavily, so the effective test sample is much smaller than 3,481. A different season could change the numbers.
5. **Timing comes from one shared Colab T4 in one session.** Training time drifted upward by about 10% over the session (4.2 s to 4.6 s). Latency includes Python overhead at batch 1. Treat timings as indicative for this machine only, and rely on the accuracy comparison, not the cost comparison.

## Why this matters here

**Target: ML engineer, load forecasting, on the analytics team of a rural electric cooperative or municipal utility** (a data group of roughly 30 people, no GPU cluster, one shared workstation or a rented T4, reporting to a state regulator and a wholesale supplier).

- **Day-ahead load forecasts drive purchasing.** Wholesale power cost and demand charges depend on the daily peak, so a forecaster that misses the 08:00 and 19:00 peaks, as the sinusoidal model partly does here, has a direct cost. Peak error is the next metric this study should add.
- **Teams like this must justify a model, not just fit one.** A model-risk or regulatory reviewer asks "better than what?" before "how accurate?". The seasonal-naive baseline is the standard answer, and this study shows a small transformer that does not clearly clear it. A recommendation to "ship the transformer" would not have survived that question.
- **There is no cluster.** The study is built so that one T4, or a CPU, reproduces it in minutes. Its compute reasoning says where the budget actually matters (seeds and real data, not GPU speed).
- **Vocabulary used here:** day-ahead forecast, MAE in MW, seasonal-naive baseline, backtest on a held-out period, peak error, out-of-time test.
